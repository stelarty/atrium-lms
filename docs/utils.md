# Utils — LMS Атриум

Данный документ описывает **правила работы с утилитами (utils)** в проекте LMS Атриум.
Цель — поддерживать единый стандарт для **переиспользуемых функций**, которые не зависят напрямую от компонентов или store, и которые могут использоваться в разных местах проекта.

---

## 1. Основная философия

* **Utils — это чистые функции**, которые:

  * не зависят от состояния компонентов или store
  * не используют DOM напрямую
  * возвращают результат
* Каждая функция имеет **одну ответственность**
* Все функции **строго типизируются** через TypeScript
* Utils не должны содержать бизнес-логику проекта

> Если функция начинает использовать store, DOM или сложные side-effect операции — её нужно вынести в **composable**, а не utils.

При этом в `utils` допустимы чистые адаптеры и валидаторы для доменных форм:
- сборка payload из draft-данных;
- маппинг API response в форму;
- чистая валидация объекта без обращения к store.

Если такая функция не делает запросы, не знает о Vue и не мутирует внешний state, она всё ещё считается `utils`.

---

## 2. Организация utils

* Каждый файл объединяет функции **по логике или назначению**, чтобы структура была понятной и масштабируемой.
* Предположительная структура может быть следующей (для будущего развития проекта):

```text
src/
└── utils/
    ├── formatters.ts       # функции для форматирования (например даты, чисел, текста)
    ├── validators.ts       # функции проверки/валидации данных
    ├── helpers.ts          # общие вспомогательные функции
    ├── course-settings.ts  # чистые мапперы/валидаторы для формы курса
    ├── api-error.ts        # сообщения об ошибках API (getApiErrorMessage)
    └── index.ts            # централизованный экспорт всех утилит
```

> Эта структура **не окончательная** — по мере добавления новых утилит могут появляться новые файлы и категории.

---

## 3. Правила и best practices

1. **Чистые функции** — без побочных эффектов, predictable output.
2. **Одно назначение** на функцию — каждая функция делает **только одно действие**.
3. **Типизация через TypeScript** — любые входные и выходные данные строго определены.
4. **Нет прямой привязки к DOM, store или компонентам**.
5. **Документировать назначение функции** через комментарии JSDoc или аналогичный стиль.
6. **Не дублировать функции** — если функция уже есть в utils, использовать её повторно.
7. **Централизованный экспорт** — через `index.ts`, если появится общий баррель для utils (сейчас импорты напрямую из файлов домена, например `@/utils/course-settings`).

---

## 4. Взаимодействие с другими слоями

* **Компоненты**: utils используются для вычислений, форматирования или проверки данных.
* **Stores**: utils используются для преобразования данных перед сохранением или отображением.
* **Composables**: utils могут использоваться внутри composables для переиспользуемой логики.

> Правильное разделение ответственности помогает проекту оставаться чистым и масштабируемым.

---

## 5. Примечания

* На данном этапе **мы не перечисляем каждую функцию** — ориентир по реализации: `src/utils/course-settings.ts` (валидация и маппинг черновика курса, форматирование дат, сбор payload).
* Любые новые утилиты добавляются **только** если они остаются чистыми функциями; иначе — composable или store.

---

## 6. Пример из проекта (`course-settings.ts`)

- `validateCourseDraft` / `buildCourseCreatePayload` — чистая валидация и сбор данных без Vue и без HTTP.
- Импортируются в **`useCourseStore`** для согласованного поведения формы и API.

Такой файл — эталон границы между «доменными правилами» и «оркестрацией в store».
