# Workflow и Best Practices — LMS Атриум

Данный документ описывает **обязательные правила разработки**, архитектурные договорённости и best practices,
которых придерживается проект LMS Атриум.  
Цель — сохранить проект читаемым, масштабируемым и понятным как для текущего разработчика,
так и для будущей команды.

**Свод правил по фактическому коду** (Axios-инстанс, старты в `main.ts`, guard’ы роутера, composables, stores): [`conventions.md`](./conventions.md).

---

## 1. Именование компонентов

### 1.1 Общие правила
- Все компоненты именуются в **PascalCase**
- Один компонент — один файл
- Название файла = название компонента

Пример:  
`TaskCard.vue` → `<TaskCard />`

---

### 1.2 Префиксы компонентов

Мы **осознанно используем префиксы**, чтобы по названию было понятно:
- уровень компонента
- его ответственность
- контекст использования

#### `Base`
Используется для **атомарных, максимально переиспользуемых компонентов**, не содержащих бизнес-логики.

Примеры:
- `BaseButton.vue`
- `BaseInput.vue`
- `BaseCheckbox.vue`
- `BaseModal.vue`

Правила:
- Не знают ничего о store
- Не знают бизнес-логики
- Получают всё через props
- Отдают всё через emits

---

#### `App`
Используется для **глобальных, инфраструктурных компонентов**, которые:
- используются по всему приложению
- тесно связаны с логикой приложения

Примеры:
- `AppLoader.vue`
- `AppToast.vue`
- `AppConfirm.vue`
- `AppTaskTimer.vue`

Правила:
- Могут работать со store
- Часто подключаются один раз (в App.vue или layout)

---

#### `The`
Используется для **уникальных, одиночных компонентов**, которые:
- существуют в одном экземпляре
- являются частью каркаса приложения

Примеры:
- `TheHeader.vue`
- `TheFooter.vue`
- `TheSidebar.vue`
- `TheProfileMenu.vue`

Правила:
- Обычно используются внутри layout
- Не предполагают переиспользование

---

#### `Widget`
Используется для **крупных, самостоятельных UI-блоков**, содержащих бизнес-логику.

Примеры:
- `WidgetCourseCard.vue`
- `WidgetTaskCard.vue`
- `WidgetProgressBar.vue`

Правила:
- Могут использовать store
- Могут включать в себя base-компоненты
- Часто документируются отдельно

---

## 2. Структура компонентов

### 2.1 Обязательная структура файла

```vue
<template>
  <!-- template -->
</template>

<script setup lang="ts">
// imports
// props
// emits
// composables
// state
// computed
// methods
</script>

<style scoped lang="scss">
/* styles */
</style>
```

Порядок обязателен — это сильно упрощает чтение чужого кода.

## 3. Props, Emits и ответственность

### 3.1 Props
- Все props строго типизируются
- Никаких `any`
- Props — только входные данные

```ts
defineProps<{
  task: Task
  disabled?: boolean
}>()
```

### 3.2 Emits
- Компонент не меняет внешнее состояние напрямую
- Все изменения — через события

```ts
defineEmits<{
  (e: 'answer-changed', value: string): void
}>()
```

---

## 4. Composables

### 4.1 Назначение
Composables используются для:
- переиспользуемой логики
- сложных реактивных цепочек
- работы с формами, таймерами, валидацией

Примеры:
- `usePhone()`
- `useFormStep()`
- `useDebounce()`

### 4.2 Правила
- Название всегда начинается с `use`
- Не содержат разметки
- Могут использовать store
- Возвращают только то, что реально нужно

---

## 5. Stores (Pinia)

### 5.1 Общие правила
- Один store — один домен
- Store = бизнес-логика
- Компоненты = UI

Примеры:
- `userStore` — пользователь
- `courseStore` — курсы
- `taskStore` — задания

### 5.2 Что НЕЛЬЗЯ делать в store
- Работать с DOM
- Использовать refs компонентов
- Хранить локальное UI-состояние компонентов

---

## 6. Формы и валидация
- Вся сложная логика форм выносится в composables
- Пошаговые формы — единый подход
- Телефон:
  - `libphonenumber-js`
  - форматирование визуальное ≠ формат для backend
  - ошибки показываются только при реальной ошибке

---

## 7. Router и Layouts
- Все страницы используют layout
- Layout определяется ролью пользователя
- Вложенные маршруты обязательны

Пример:
```ts
/student
  → MainLayout
    → Dashboard
    → Courses
```

---

## 8. Styles

### 8.1 БЭМ
Проект использует **классический БЭМ**:

- `block-name`
- `block-name__element-name`
- `block-name--modifier-name`
- `block-name__element-name--modifier-name`

📌 Подробные правила описаны в **docs/styles.md**

### 8.2 SCSS
- Глобальные переменные — `styles/base`
- Миксины — `styles/mixins`
- Компоненты — scoped стили

---

## 9. Документация как часть workflow
- Новый компонент → запись в `/docs/components`
- Новая страница → по договорённости команды (при необходимости `/docs/pages`)
- Новый store / composable → актуализация [`conventions.md`](./conventions.md) или профильных `*.md`
- Документация пишется параллельно коду, а не после.
